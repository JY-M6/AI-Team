# 钱迹决策记录

## Decision 001：页面端先于微信小程序端

决策内容：
先做响应式页面端原型，确认手机端和电脑端效果后，再拓展到微信小程序端。

决策原因：
页面端迭代快，便于先确认信息结构、视觉风格和交互逻辑；钱迹的主用户仍以手机用户为主，所以页面端必须手机优先。

影响范围：
当前阶段先在 `frontend/` 下实现 Vue 3 + Vite 响应式页面，不直接进入微信小程序工程。

风险：
页面端与小程序端存在组件和交互差异，后续迁移时需要重新适配小程序能力。

是否需要用户确认：
已确认。

## Decision 002：AI 采用全模块自动分析

决策内容：
AI 不作为单独页面孤立展示，而是嵌入总览、记账、日历、每日明细、统计和理财等模块中，自动给出分析。

决策原因：
用户希望强调“自动帮助分析”，而不是让用户主动进入 AI 页面提问。

影响范围：
页面结构从独立 AI 模块调整为多处内嵌 AI 提示卡。

风险：
后续真实接入 API 时，需要控制调用频率、隐私授权和分析触发时机。

是否需要用户确认：
已确认。

## Decision 003：理财展示到具体产品

决策内容：
理财模块按常识分类展示产品，先分为 ETF 基金、主动基金、现金管理、存款、债券固收等类别；每个类别下展示相应产品，点击产品后进入该产品详情，展示走势、持仓、风险和 AI 产品分析。

决策原因：
用户希望理财不是泛泛展示“货币基金、债券基金”，而是能查看自己真实购买或关注的具体产品，例如半导体 ETF、沪深 300 ETF。

影响范围：
理财模块需要支持分类、产品列表、产品详情、产品名称、代码、持仓金额、风险等级、走势、更新时间和 AI 分析。

风险：
真实行情数据涉及第三方 API、更新频率、合规提示和成本控制。

是否需要用户确认：
已确认。

## Decision 004：钱迹功能清单分层管理

决策内容：
钱迹完整功能清单按核心基础功能、统计分析功能、进阶实用功能、小程序体验与轻量化配套、后端管理功能、可选变现增值模块分层管理。

决策原因：
功能范围较大，必须区分刚需、留存、差异化、后台和商业化，避免 MVP 阶段失焦。

影响范围：
需求文档需要维护功能优先级；页面端当前只覆盖 P0 和部分 P1 原型，不直接实现后台和变现模块。

风险：
如果不控制优先级，项目会从记账 MVP 膨胀成完整商业平台，开发周期不可控。

是否需要用户确认：
已确认。

## Decision 005：记账时间精确到分钟

决策内容：
记账表单增加时间字段，精确到分钟，默认值为用户记账时的当前时间。

决策原因：
每日明细和 AI 分析需要更准确地判断消费发生时间，例如午餐、晚间购物、通勤等场景。

影响范围：
后续账单模型和接口必须保存分钟级时间，而不能只保存日期。

风险：
需要处理用户手动修改时间、跨天补记和时区问题。

是否需要用户确认：
已确认。

## Decision 006：UI 参考方向待按视频确认

决策内容：
用户喜欢的是提供的视频中的 UI 设计，不是当前页面端原型本身。后续需要获取视频画面后，提取其布局、配色、组件质感和动效风格，再迁移到钱迹页面端。

决策原因：
用户澄清：“我是说我给你发的那个视频里面那个 ui 设计，我很喜欢。”

影响范围：
当前页面端原型仍可作为功能结构验证稿，但视觉风格不能视为最终确认稿。后续 UI 调整应以视频为主要视觉参考。

风险：
视频参考已用于交互动效设计，但 Web 页面和微信小程序的动画能力不同，迁移时仍需重新适配并验证性能。

是否需要用户确认：
已确认。

## Decision 007：视频参考重点调整为动态交互

决策内容：
用户进一步澄清：喜欢视频里的 UI，主要是喜欢其中的动态交互，而不是要求页面静态视觉完全照搬。当前页面端应优先吸收视频中的滚动入场、卡片漂浮、切换反馈、走势图绘制和轻量高亮动效。

决策原因：
钱迹是高频日常小程序，用户每天都会打开查看账单、日历、统计和理财产品。动效应服务于“自然、顺滑、自动反馈”，让用户感觉 AI 分析和数据切换是实时发生的，而不是单独跳转页面。

影响范围：
当前 `frontend/` 页面端加入动态交互原型；后续迁移微信小程序端时，需要用小程序动画能力重做对应手感，不直接照搬 Web API。

风险：
动效不能影响手机端性能，也不能喧宾夺主。已加入 `prefers-reduced-motion` 兜底，后续小程序端还需要单独做性能验证。

是否需要用户确认：
已确认。

## Decision 008：第一版后端采用模块化单体

决策内容：
第一版建议采用 Spring Boot 3 模块化单体和 MySQL，以账单为事实数据源；日历、统计、预算、AI 和理财按模块边界组织，不拆微服务。

决策原因：
当前核心链路仍处于第一版开发阶段，模块化单体可以保持事务一致性和开发效率，也能通过清晰模块边界为后续拆分留出空间。

影响范围：
后端工程结构、数据库事务、接口分组和开发顺序以 [架构分析](architecture.md) 为基线。

风险：
登录方式、AI 供应商和理财行情数据源尚未确认，相关实现必须通过适配器隔离，不能写死供应商。

是否需要用户确认：
进入后端编码前确认。

## Decision 009：后端采用 WebFlux + SSE

决策内容：
后端采用 Spring WebFlux。账单、账户、日历、统计等普通业务接口继续使用 REST + JSON；AI 对话与自动分析通过 SSE 返回增量内容。

决策原因：
AI 输出耗时较长，流式返回可以降低等待感，并支持各页面内嵌分析逐步呈现。SSE 符合当前服务端单向推送需求，不需要为第一版引入 WebSocket。

影响范围：
后端依赖、Controller 返回类型、AI 供应商适配器、超时取消、前端流式解析和 AI 分析记录状态均按响应式链路设计。

风险：
MySQL 访问层必须采用响应式驱动，不能在 Netty 事件线程中混用阻塞式 JDBC/MyBatis-Plus；第三方模型 SDK 若仅支持阻塞调用，需要隔离到有界线程池或改用响应式 HTTP 客户端。

是否需要用户确认：
用户已确认。

## Decision 010：数据库层采用 Spring Data R2DBC，彻底剥离 MyBatis-Plus

决策内容：
运行时持久化层全面采用 `Spring Data R2DBC` + `r2dbc-mysql` 驱动加 `ReactiveTransactionManager` 进行非阻塞事务控制。在任何运行时事件线程中彻底禁止使用 JDBC 或 MyBatis-Plus。

决策原因：
坚持 WebFlux 的非阻塞模型。如果在 WebFlux 的核心 Netty 事件循环中混用阻塞的 JDBC，会导致线程池耗尽，性能反而恶化。Flyway 仅在启动阶段使用 JDBC 迁移数据库，不影响运行时高并发，因此予以保留。

影响范围：
后端所有数据库操作均需编写响应式流式 DSL（基于 `DatabaseClient` 或响应式 Repository）。放弃传统的 MyBatis / MyBatis-Plus 等阻塞框架。

风险：
响应式数据库访问调试难度高，国内生态圈对于 R2DBC 的 ORM 库支持少，部分高级 SQL 聚合和多表关联需要通过手写拼装或手动映射处理，开发周期略微拉长。

是否需要用户确认：
用户已确认。

## Decision 011：转账设计为单记录双账户关联，账户保存余额快照

决策内容：
转账（`TRANSFER` 类型交易）不拆分成转出和转入两条独立流水，而是作为单条流水保存。流水表中通过 `account_id` 记录转出方，`target_account_id` 记录转入方。在同一个响应式事务中，扣减转出账户余额，增加转入账户余额。账户表保存实时 `balance` 快照，手动校准时生成系统平账流水。

决策原因：
如果拆为两条流水，在非阻塞数据库下做多表/多行一致性修改极其复杂。单记录转账设计能极大简化删除、修改账单时的事务逻辑。账户保存余额快照能避免在首页加载资产总览时高频聚合全量账单导致的慢查询。

影响范围：
`transactions` 表结构设计、转账接口、账单编辑删除接口和账户校准接口。

风险：
如果响应式事务失效，可能造成两个账户余额扣减和增加不一致，后端必须配备严格的声明式事务切面和校验。

是否需要用户确认：
用户已确认。

## Decision 012：AI 对话与敏感财务记忆后置，确立隐私安全红线

决策内容：
1. 将“多轮会话（P1）”和“长期记忆（P2）”从第一阶段（P0）的核心记账链路中剥离后置。
2. 规定 AI 对话记录采取 `PENDING` 到 `COMPLETED` 占位状态机，流式断网时标记为 `FAILED/CANCELLED`。
3. 长期财务记忆必须具备严格隐私防线：用户显式授权、支持物理删除、区分“用户陈述”与“AI 推算”，且销户时物理清空。

决策原因：
防止 MVP 首发版本范围无限膨胀，保障记账和单次分析的核心链路尽快跑通。同时，用户的财务隐私画像属于极度敏感数据，必须在设计阶段就明确红线，防止被滥用。

影响范围：
后端实体表结构（部分划分为 P1/P2 后置）、接口排期、AI 服务上下文提取机制。

风险：
多轮会话和记忆后置可能使得初期 AI 的个性化体验略显单一，但核心的单次分析（哈希限频）已足够支撑首版验证。

是否需要用户确认：
用户已确认。

## Decision 013：模型输出必须经过后端校验后再流式重放

决策内容：
模型原始输出统一视为不可信外部输入。后端必须先缓冲完整结果，执行严格 JSON 结构、证据键、金额事实、内容安全和理财合规校验；校验通过后才保存并向前端发送。需要流式视觉效果时，对已校验结果重新分块发送，禁止透传上游模型 token。

决策原因：
钱迹处理账单与理财信息，模型可能虚构金额、产品或收益，也可能输出脚本、提示词泄漏和越权操作建议。Prompt 约束不能替代后端校验，核心事实必须以服务端确定性计算为准。

影响范围：
AI 模型适配器、SSE 状态机、分析记录表、错误码、缓存、审计日志和测试用例。`ai_analysis_records.result_json` 仅保存校验后结果，不保存失败的模型原文。

风险：
完整校验后再重放会增加首个正文分块的等待时间。客户端可先展示 `GENERATING` 和 `VALIDATING` 进度事件，但不能以降低等待感为由绕过校验。

是否需要用户确认：
用户已确认。
