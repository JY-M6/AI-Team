## 项目定位

AI-Team 是一个用于统一管理多个项目的 AI 团队母仓库。

它不是单一项目，也不是普通笔记仓库，而是一个可持续扩展的项目工作台：后续每个真实项目都会放在 `projects/` 目录下，并拥有自己的需求文档、接口文档、部署文档和项目级 `README.md`。

这个根目录 `README.md` 的职责是：

- 让访问仓库的人快速理解 AI-Team 是什么。
- 统一说明仓库结构、团队角色和协作方式。
- 作为所有子项目的总索引。
- 引导读者进入具体项目的独立 README。

## 推荐项目结构

```text
projects/<project-name>/
├── AGENTS.md
├── README.md
├── backend/
├── frontend/
├── docs/
│   ├── requirements.md
│   ├── api.md
│   ├── database.md
│   ├── ai.md
│   └── deployment.md
└── deploy/
    ├── docker-compose.yml
    └── nginx/
```

每个子项目的 `README.md` 建议包含：

| 部分 | 内容 |
|---|---|
| 项目简介 | 项目解决什么问题，面向什么用户 |
| 功能清单 | 已完成、开发中、暂不做的功能 |
| 技术栈 | 前端、后端、数据库、AI 能力、部署方式 |
| 快速启动 | 本地启动步骤、环境变量、依赖说明 |
| 目录结构 | 子项目内部模块说明 |
| 接口说明 | 接口文档入口或关键接口摘要 |
| 部署说明 | Docker、Nginx、环境变量和健康检查 |
| 演示说明 | 演示账号、演示流程、截图或链接 |

## 团队角色

AI-Team 通过角色分工推进项目。用户可以在任务中直接使用 `@角色名` 调用对应视角。

| 角色 | 职责 |
|---|---|
| `@项目总控` | 拆解任务、控制范围、安排角色、汇总结论 |
| `@产品经理` | 明确目标用户、MVP、功能优先级和验收标准 |
| `@需求分析师` | 梳理业务对象、流程、状态、权限和异常 |
| `@架构师` | 设计系统结构、模块边界、数据流和开发顺序 |
| `@UI设计师` | 设计页面结构、交互、组件和状态 |
| `@前端工程师` | 实现页面、组件、状态管理和接口联调 |
| `@后端工程师` | 实现接口、服务、数据访问、校验和异常处理 |
| `@AI工程师` | 设计 Prompt、RAG、Agent、结构化输出和防幻觉策略 |
| `@数据库工程师` | 设计表结构、索引、关系和缓存结构 |
| `@测试工程师` | 编写测试用例、复现问题和回归验证 |
| `@代码审查员` | 审查 diff、风险、测试覆盖和合并建议 |
| `@运维部署工程师` | 设计部署、环境变量、Docker、日志和回滚 |
| `@文档工程师` | 编写 README、接口文档、部署文档和使用说明 |
| `@答辩顾问` | 整理项目亮点、演示流程、PPT 大纲和答辩话术 |

## 工作原则

- 先明确目标、假设、风险和验收标准，再推进任务。
- 修改前先读相关文件，不猜接口、不脑补业务。
- 默认最小改动，不做无关重构、格式化或架构调整。
- 普通读取操作可以主动执行；普通修改操作需要先说明影响范围。
- 删除、生产部署、真实数据修改等高风险操作必须由用户明确确认。
- 修改运行时代码后必须执行对应验证；无法验证时必须说明原因。
- 所有文档必须基于真实代码和真实功能，不编造能力。

## 推荐工作流

```text
需求想法
  ↓
@项目总控 拆解任务和控制范围
  ↓
@产品经理 / @需求分析师 明确 MVP 与业务规则
  ↓
@架构师 / @UI设计师 设计技术方案与页面结构
  ↓
@前端工程师 / @后端工程师 / @AI工程师 小步实现
  ↓
@测试工程师 验证功能
  ↓
@代码审查员 检查风险
  ↓
@文档工程师 同步 README 与项目文档
```

## 使用示例

```text
@项目总控

```

```text
@产品经理
帮我明确这个项目的 MVP，最多问我 5 个关键问题。
```

```text
@代码审查员
请审查当前 git diff，并给出是否建议合并。
```
